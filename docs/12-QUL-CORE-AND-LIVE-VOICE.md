Status: implementation contract · 2026-10-01. This document supersedes earlier source, schema-version, navigation, and one-shot-only UI descriptions where they conflict. The existing `POST /v1/voice/detect` remains for shared files and compatibility.

## Priority and source boundary

3. Implement the four-tab shell and put the mic control **only as a floating button on the Mushaf screen, outside the printed page**. The app opens on the Surah list. For this milestone, Latin transliteration, hadith, tafsir, and Surah meanings are hidden and have no legacy content fallback. The independent Tarteel ASR model and non-Qur'an daily-needs providers remain.

The QUL ZIPs and fonts are local build inputs. The source archives inspected so far contain no redistribution-license files. Until resource-specific rights are established, generated content and fonts stay untracked and local; do not publish an APK, IPA, Git artifact, or download endpoint containing them. See docs/10 and QUL's resource guidance.

GitHub CI can run source-independent audits and Dart source analysis. It cannot rebuild or package the QUL database or print assets while these inputs remain untracked. Full data verification, Flutter analysis, and reader tests run locally; a green CI check alone does not establish content validity or release readiness.

## Immutable database contract

`quran.sqlite` v2 has `meta.db_version=2` and `PRAGMA user_version=2`. Its `surah` table keeps number, QUL Arabic/simple names, count, revelation order/place, first 1405H page, and `bismillah_pre`; meaning fields are nullable and remain null. Its `ayah` table keeps the existing ID/key/text/translation columns for API and app compatibility; `text_latin`, `translation_en`, `hizb_quarter`, `ruku`, and `manzil` are null; `hizb` is 1..60. No tafsir rows are populated. Search normalization never changes display text. `page` has 604 rows; `juz` 30; `hizb` 60; `sajda` is source checked. The QUL 1405H layout and word data determine the first page for each canonical ayah; a long ayah may occupy more than one page. Version 3 adds all line and word memberships, font hashes, and a fixed rendering profile.

The installer verifies the bundled SHA-256 and schema version before replacing its local `quran.sqlite`. It does not replace `user.sqlite`; bookmark, note, and last-read keys remain canonical. A failed content install keeps prior verified content and reports that the new print view is unavailable. A v2 semantic database alone cannot satisfy the v3 print renderer.

The backend matching index is rebuilt from the exact installed v2 semantic corpus and records the source DB checksum. Voice response `surah_name_translation` is nullable. No backend response page number is trusted for print navigation; the app resolves each canonical ayah through the active local edition.

## Printed page and ayah interaction

The renderer paints the prescribed QUL line sequence in fixed page coordinates, using that page's exact V1 font. It measures word and numbered end-marker hit boxes from the same shaped glyphs. Touch and highlight use the same page-fit, zoom, pan, and inset transform. Tap or long press on any word/end marker selects its canonical ayah; headings, unnumbered basmala, ornaments and blank areas do not select. Selection paints each segment separately across lines and pages, opens actions for Indonesian translation, bookmark, copy, and share; copy/share use QUL canonical Uthmani text. Tafsir, transliteration, and audio controls are absent until their own sources/features are ready. An incoming `2:255` link resolves to page 42 and pulses only that ayah for four seconds. Page 48 must support selection of the multi-line `2:282` without selecting neighbors. Default page fit displays the whole print; zoom never changes line membership.

The local visual proof keeps the KFGQPC V1 `surah_name` row and uses the user-supplied QUL Surah header font archive (resource 458) for its complete colored title ornament. Its 114 glyph mappings are pinned as a local build input. The staging tool rasterizes these color glyphs to hash-verified transparent PNGs because Flutter's text layout reports this font's ink bounds poorly; the source is still the exact QUL color font. QUL Surah name font v2 (resource 455) supplies the compact top-left reader label; it does not replace the V1 page text font. The QUL common font (resource 459, already used for basmala) supplies the Juz glyph in the compact top-right reader control; the Hizb number comes from the canonical ayah metadata. The header identifies the first visible ayah on the current print page, including pages that begin in the middle of a long ayah. A bottom control shows `Halaman x / 604` and opens the existing jump sheet. Native iOS back gesture and Android system back handle return from the reader; no visible back button is shown. Keep reader controls outside the print canvas, remove the provisional outer rectangle, align the source lines close to the available screen width, and preserve their fixed membership. Selected ayat receive a continuous translucent band for each visible line segment, rather than separate colored word boxes; individual word hit targets remain. These decorative fonts and mappings stay in the ignored local pack while redistribution rights are unresolved.

## Live Voice Finder protocol

Live listening is a new, distinct contract. The Flutter mic starts 16 kHz mono PCM capture and a WebSocket session at `/v1/voice/live`. After a server `ready` event, the client sends binary PCM chunks in capture order (target 0.5–1 second each) and may send a JSON `stop` message. The server starts matching at 1.5 seconds, schedules another window after each further second when inference capacity is available, and bounds retained audio to a four-second rolling window. It processes each window asynchronously with the existing Tarteel Whisper model and matcher, and sends JSON `candidate`, `ayah`, `ambiguous`, or `error` events with a monotonically increasing `sequence`. `ayah` includes canonical `surah`, `ayah_start`, `ayah_end`, confidence and a session-local stable revision; only a new stable revision updates the printed highlight. Matching uses hysteresis and continuity so a noisy window cannot jump rapidly to unrelated repeated ayat. The mobile page follows new stable ayat while listening, including page turns; it resolves the end ayah's page from the installed QUL database and highlights the full canonical range. The server's page field is not trusted. The user can pause follow while recording continues; resuming navigates to the most recent stable result. Connection loss stops capture and displays retry; it never silently stores audio.

The mobile transport sends fixed 16,000-byte half-second PCM frames and allows at most two queued frames beyond the one being sent. Queue overflow stops capture and shows retry. The backend permits one active inference per session, limits simultaneous inference to its configured ASR worker count, rejects an overloaded inference after two seconds, and keeps the existing per-device rate and connection limits. A session expires after 180 seconds. Errors include `INVALID_PCM_FRAME`, `INVALID_COMMAND`, `BACKPRESSURE`, `SESSION_EXPIRED`, and `INFERENCE_FAILED`; the session closes after an error. Invalid client metadata closes with 4400, while rate or connection limits close with 4429. No raw audio or transcript is persisted or logged by default. See [docs/05 §2.1a](05-BACKEND-API-SPEC.md) for event fields.

The existing one-shot endpoint is retained for shared files and compatibility. Live latency, accuracy, and repetition handling require a recorded, consented streaming golden set; the current golden set has zero samples, so no accuracy figure is claimed. The first live implementation must have protocol tests, cancellation and disconnect cleanup, repeated-ayah cases, bounded-memory checks, and a device proof that reciting successive ayat advances the highlight.

## Live recognition preview and microphone recovery (2026-10-06)

The Mushaf mic shows a compact status/recognition strip outside the printed page. Connecting and listening states expose Stop; permission denial, timeout, disconnect, backpressure, session expiry, and inference failure show localized status and Retry. Result events may carry the latest raw ASR `transcript`, limited to 1,000 Unicode characters. Before the first stable match, render it RTL in Me Quran at 14 logical pixels, regular weight and muted gray-green, and label it as recognition text that may change. Replace the latest nonempty preview rather than concatenating overlapping windows. Preview events never navigate; existing stable ayah revisions and local QUL page resolution control navigation. Clear and hide the preview and its label once the first stable ayah is found, including while follow is paused; keep them hidden for the rest of that session. Listening continues after a match. Before that first match, Pause follow still allows preview updates; Resume follows the latest stable ayah. Clear text and stop capture on Stop, backgrounding, disposal, or failure; ignore prior-session events. No waveform, word timing, correctness scoring, or audio/transcript persistence is added.

Development diagnostics must verify that the configured API is reachable and Redis, the ASR model, and matcher index are ready. The default API URL is `http://localhost:8000` for iOS Simulator; Android Emulator uses `http://10.0.2.2:8000`. A green button alone is not proof that the server is running. Device UI must expose failures instead of silently returning to idle.
